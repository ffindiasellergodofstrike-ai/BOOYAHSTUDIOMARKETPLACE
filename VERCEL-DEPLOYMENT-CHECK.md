# GitHub + Vercel API deployment check

Updated 23 October 2026. These are deployment requirements and local checks, not a claim that an external Vercel project, credentials or payment account has been configured.

## Build and routing

Import the private repository root containing `package.json` and `vercel.json`. The config explicitly selects Vite, frozen-lockfile installation and `dist` static output. Use Node 24.x and the pinned pnpm version. Keep the `api/` directory: it is the backend; uploading only `dist` cannot support login, admin writes, payment verification or private downloads.

`api/index.ts` directly exports the Express application from the private Node-compatible `build/api-app.mjs` bundle generated by the full build command. Keep that direct export: Vercel detects Express and lets its middleware read the original request stream, including signed webhook bytes. Do not wrap this export in a generic function that first parses or reconstructs the request body.

The first rewrite sends `/api/*` to the backend, before SPA fallback. Product-share pages use `api/page.ts`; both functions explicitly trace the private API bundle, and page rendering traces `dist/index.html`. The API function has a 300-second maximum and the product-page function has a 60-second maximum. Current Vercel Fluid Node.js plans support a 300-second function budget; if your project has legacy non-Fluid limits, enable Fluid or use a supported budget and smaller scheduled batches. Interactive clients still use shorter timeouts and must reconcile uncertain outcomes. Canonical policy pages remain static, while old policy aliases and categories added after the build reach the client router instead of nonexistent generated files.

`.vercelignore` excludes archives, editable paid sources, local secrets, dependencies and old build output from deployment inputs. The build recreates client output; public preview assets remain included. This ignore file does not make a public GitHub repository safe: paid source archives still require a private repository.

## Origins, sessions and environment settings

Set `APP_URL` to the exact public HTTPS origin customers use, including the intended www/non-www host and no path/query. Session cookies are host-bound. Choose one canonical public host in Vercel and redirect the alternate host at the platform.

If `APP_URL` is absent on Vercel, the backend derives the origin from trusted Vercel deployment environment variables. An explicit `APP_URL` always wins. Set Preview values separately from Production; a Preview site using a Production `APP_URL` will correctly reject cross-origin state-changing requests. Register the corresponding trusted Auth redirects in the appropriate Supabase environment. Do not broaden CORS to arbitrary origins or trust client Host headers to generate recovery/payment links.

Configure the Supabase, Cashfree, Resend and cron variables described in `SETUP-HINDI.md`, then redeploy. None of these services are created by a Vercel build. A successful static build or `/api/health` response alone does not prove database access, storage policies, Auth email delivery or live payment readiness.

## Upload and function limits

Vercel Functions have a 4.5 MB request/response payload limit. API-proxied thumbnails and dispute attachments are limited to **4 MB** to leave room for multipart fields. Larger Cashfree evidence must be submitted through the Cashfree Dashboard. Paid ZIPs upload directly to private Supabase Storage using authorized signed upload URLs or the Storage dashboard; do not send large paid files through the Vercel API. Raising Multer limits or function duration cannot override the platform payload limit.

Supabase SDK requests use a 10-second request timeout and retain caller cancellation. Provider calls and reconciliation can take time. Keep bounded batches, scheduled retries and durable records; a function timeout can leave an external result unknown. Reconcile before issuing another financial action. A request timing out is not evidence that payment, refund or evidence submission failed at the provider.

## Diagnose actual errors

API error responses include a safe message and request reference when the request reaches the application's error handler. Malformed JSON is a 400 and an oversized body is a 413; upstream/application failures are reported as unavailable, not converted into empty successful dashboards. For platform-level errors such as 413/504, check the HTTP status, Vercel invocation logs and deployment settings. Do not paste secret keys or full webhook/recovery payloads into logs or support tickets.

After deploying, verify on the actual configured domain:

1. `/api/health` is JSON, not `index.html`; an unknown `/api/*` path returns JSON 404.
2. Public catalog and direct product pages load current data and built assets.
3. Direct `/admin`, `/login`, `/register` and `/forgot-password` visits/refreshes resolve.
4. Unauthenticated admin API requests fail with 401/403; customer accounts cannot administer products.
5. Signed-in owner changes persist after refreshing and another browser session sees the published catalog changes.
6. A new Auth email and recovery email reach a real inbox and return to the same trusted origin.
7. Sandbox checkout, signed webhook, private download ownership and duplicate-event protection work on the deployed backend.
8. Large product ZIP uploads go directly to private Storage; missing files fail closed before checkout.
